## 2. 보안 검토 범위와 방법

**대상**: 위 표의 모든 신규/수정 파일 (신규 API 클라이언트 3개 + 페이지 6개 + 컨텍스트 1개).

이 프로젝트의 신뢰 경계는 명확합니다: **모든 인증/인가·소유권 검증은 백엔드(Spring)가 수행**하고, 프론트는 `src/api/client.ts`의 공용 `api` 래퍼로 JWT를 붙여 요청만 보냅니다. 따라서 "프론트에 권한 체크가 없다"는 이번 검토에서 취약점으로 잡지 않았습니다 (백엔드가 신뢰 경계이기 때문).

## 3. 점검 카테고리별 결과 (전부 미탐지 — 아래는 "왜 아니라고 판단했는지")

| 카테고리 | 점검 방법 | 결론 |
|---|---|---|
| **XSS** | 변경 파일 전체에서 `dangerouslySetInnerHTML`, `innerHTML`, `eval(`, `new Function`, `document.write` 검색 | 0건. AI 채팅 답변, AI 생성 문제, 문의 내용, 관리자 답변 등 사용자/AI가 만든 텍스트는 전부 `{value}` 형태의 JSX 텍스트 보간으로만 렌더링됨. React는 이 경로를 자동 이스케이프하므로 HTML/스크립트 주입 경로 자체가 없음 |
| **오픈 리다이렉트 / 안전하지 않은 URL** | `href`, `window.location`, `target="_blank"` 등 사용자·AI 제어 데이터로 URL을 만드는 코드 검색 | 0건. 새로 추가된 카페/오피스 공지 클릭 영역도 `onClick={() => setShowNotice(true)}` 뿐으로 데이터 흐름 없음 |
| **하드코딩된 시크릿/키** | `aiApi.ts`, `inquiryApi.ts`, `studyApi.ts` 검토 | 없음. 기존 `client.ts`의 `BASE_URL`/`api.get·post·put·del` 패턴만 재사용 |
| **민감정보 노출/로깅** | `console.log`, `localStorage`/`sessionStorage` 쓰기 검색 | 없음. 토큰 저장 방식은 기존 `client.ts` 그대로(변경 없음), 이번 diff에서 새로 로깅하거나 저장하는 값 없음 |
| **인젝션(SQL/커맨드/템플릿)** | 요청 바디 구성 방식 확인 | 전부 구조화된 JSON으로 `client.ts`의 `JSON.stringify` 경유. 문자열 결합으로 URL/쿼리를 만드는 곳 없음 (쿼리 파라미터는 `URLSearchParams.set()` 사용) |
| **인증/인가 로직** | `isSecret`(비밀글), 관리자 전용 엔드포인트 호출부 확인 | 프론트는 값만 그대로 백엔드로 전달하고 별도 검증을 시도하지 않음 — 설계상 의도된 것이며 백엔드(`InquiryService`)가 소유자/관리자 검증을 전담 |
| **경로 순회(Path Traversal)** | 파일시스템 접근 코드 검색 | 해당 없음. 이번 diff는 전부 HTTP 호출 + React 렌더링 |

## 6. SpotBugs(+FindSecBugs) 정적 분석 — `studyforest_server` (백엔드, 읽기 전용 분석만 수행·코드 미변경)

`./gradlew spotbugsMain` 실행 결과 (`build/reports/spotbugs/main.html`): 총 88건 (Medium 88 / High 0), 이 중 "Security Warnings" 카테고리 6건을 직접 코드 대조해 검증:

| 건수 | 유형 | 위치 | 판정 | 근거 |
|---|---|---|---|---|
| 4건 | `SQL_INJECTION_SPRING_JDBC` | `AdminService.java` (95, 105, 321, 331행) | **오탐** | `StringBuilder where`에 이어붙이는 조각은 전부 `" AND ... = ? "` 같은 하드코딩 SQL 구조 리터럴뿐이고, 실제 사용자 입력값(`keyword`, `era` 등)은 전부 `params` 리스트에 담겨 `?` 파라미터 바인딩으로만 전달됨. FindSecBugs가 "SQL 문자열을 StringBuilder로 조립했다"는 패턴만 보고 taint 소스를 구분 못해 일괄 플래그하는 전형적 오탐 |
| 2건 | `XSS_SERVLET` | `CustomAccessDeniedHandler.java:37`, `CustomAuthenticationEntryPoint.java:37` | **오탐** | 응답 `Content-Type`을 `application/json`으로 명시 설정하고, 쓰는 내용도 고정 문자열("접근 권한이 없습니다" 등)이라 사용자 입력이 전혀 섞이지 않음. `PrintWriter.write()` 호출 자체만 보고 플래그하는 패턴 |
| 나머지 82건 | 대부분 `EI_EXPOSE_REP`/`EI_EXPOSE_REP2` (내부 표현 노출) | 여러 DTO/엔티티 | 미검토 | Java record/엔티티가 필드를 그대로 반환하는 구조적 특성상 나오는 저위험 스타일 경고 다수 포함. 보안 취약점이라기보다 방어적 복사 여부에 대한 코드 스타일 이슈에 가까워 이번 세션에서는 상세 분류하지 않음 |

**결론**: FindSecBugs가 잡은 "Security" 카테고리 6건은 전부 검증 결과 오탐. 백엔드 코드는 수정하지 않았습니다 (분석만 수행).
