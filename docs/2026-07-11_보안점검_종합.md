### 3-3. Malicious code vulnerability 67건 — `EI_EXPOSE_REP`(19) / `EI_EXPOSE_REP2`(48)

**판정: 코드 패턴 자체는 실제(오탐 아님) — 그러나 이 저장소 구조에서는 보안 취약점으로 이어지지 않음.** SpotBugs가 지적하는 사실 자체(getter/생성자가 내부 필드를 방어적 복사 없이 그대로 노출)는 맞지만, "왜 실제 공격으로 이어지지 않는지"는 유형별로 다음과 같이 나뉩니다.

**(A) DTO(record)가 리스트/객체를 그대로 반환 — `EI_EXPOSE_REP` 19건 + 대응 생성자 `EI_EXPOSE_REP2`**
위치: `AdminQuestionDetailResponse.choices()`, `AiGeneratedQuestionDetailResponse.choices()`, `AiGeneratedQuestionSetDetailResponse.questions()`, `GenerateAiQuestionResponse.questions()`, `GeneratedQuestionResponse.choices()`, `DashboardResponse.recentActivities()`, `InquiryDetailResponse.comments()`, `MockExamSaveAnswersRequest.answers()`, `MockExamSubmitRequest.answers()`, `MockExamResultResponse.answers()`, `MockExamStartResponse.questions()`, `PageResponse.content()`, `QuestionDetailResponse.options()`, `WeaknessAnalysisResponse.items()`, `VoiceJoinResponse.participants()` 등.
- 근거: 이 record들은 컨트롤러에서 만들어져 Jackson이 즉시 JSON으로 직렬화한 뒤 버려지는 응답 객체(또는 컨트롤러가 받자마자 검증 후 소비하는 요청 객체)라, 외부 공격자가 이 리스트에 대한 참조를 얻어 서버 내부 상태를 변형할 수 있는 경로가 없음.

**(B) 엔티티 getter가 연관 엔티티를 그대로 반환 — `Inquiry.getMember()`, `SeatOccupancy.getMember()`, `StudySession.getMember()`**
- 근거: 이론적으로는 호출한 쪽이 반환된 `Member` 객체의 setter를 호출해 JPA 더티체킹으로 의도치 않게 DB에 반영될 "여지"는 있음(캡슐화 관점에서는 개선 여지 있는 코드). 다만 이 프로젝트에서 이 getter들이 컨트롤러 응답으로 직접 노출되는 경로는 없음(전부 `xxxResponse.from(entity)`로 DTO 변환 후 반환) — 즉 **외부에서 트리거 가능한 공격 경로 없음**. 내부 코드 품질 이슈에 가까움.

**(C) 서비스/컨트롤러 생성자가 Spring 빈(레포지토리, `JdbcTemplate`, `ObjectMapper`, `RestClient`, 다른 서비스 등)을 그대로 저장 — `EI_EXPOSE_REP2` 나머지 전부** (예: `AdminController`, `AdminService.jdbcTemplate`, `AiController.aiService`, `AiService.aiRestClient`/`objectMapper`, `CustomAccessDeniedHandler.objectMapper`, `CustomAuthenticationEntryPoint.objectMapper`, `InquiryController`/`AdminInquiryController.inquiryService`, `JangwonController`/`AdminJangwonController.jangwonService`, `NoticeController`/`AdminNoticeController.noticeService`, `QuestionController`/`WrongAnswerController.questionBankService`, `StudyAnalysisService.jdbcTemplate`, `SeatEventPublisher`/`SeatEventSubscriber`/`StudySpaceWsController`/`WebSocketEventListener`/`PresenceService`/`SeatHoldService`/`StudySpaceStartupCleaner`(Redis·메시징 관련 다수), `TodoController.todoService`, `VoiceWsController`/`VoiceRoomService`(메시징·Redis) 등)
- 근거: 전부 Spring 생성자 주입(constructor injection)으로 받은 싱글턴 빈을 저장하는 표준 패턴. "외부에서 변경 가능한 객체를 저장한다"는 SpotBugs 지적은 문자 그대로는 맞지만, 여기서 그 객체는 공격자가 아니라 Spring 컨테이너가 주입하는 프레임워크 싱글턴이라 이 패턴은 Spring/DI 기반 코드 전체에서 사실상 항상 오탐에 가까움.

프론트/백엔드 애플리케이션 코드 자체에서는 실제로 악용 가능한(exploitable) 취약점을 찾지 못했습니다. 실질적 리스크는 프론트엔드 의존성(`react-router-dom`/`vite`) 버전 하나이며, 조치 방법은 검증까지 끝났지만 적용은 보류 중입니다.
